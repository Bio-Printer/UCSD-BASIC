# BC -- design notes

BC is a BASIC compiler written in BASIC.  It runs on the UCSD Pascal II.0
P-System (the emulator UCSD-Pascal_Windows_Emulator) and produces II.0
code files.  It compiles itself there: the code files it makes of its own
sources are byte for byte the ones the host build makes (tools/selfcompile
.py), and so is the run-time library.

## 1. The pieces

BC is six programs, each in memory alone: one CHAINs to the next (the
library's CHAIN, Tiny-C's pexec protocol: section 9), so each has all of
memory for its own code and tables.

    BC.CODE      the driver: bc.bas
    BCLEX.CODE   pass 1: bclex.bas (source -> token file), bckw.bas
    BCGEN.CODE   passes 2 and 3: bcgen.bas (statements, procedures),
                 bcdecl.bas (declarations; segment DECL), bcexpr.bas
                 (expressions), bcemit.bas (the emitter, jumps, entry and
                 exit code, the object file), bctok.bas (the token reader,
                 the symbol table), bckw.bas; pass 3 in the segments STMT,
                 STMTA, STMTD, STMTIO, EXPR and EXPRGEN (section 10)
    BCLIST.CODE  the listing and its disassembler: bclist.bas
    BCLINK.CODE  the linker and -J: bclink.bas
    BCERR.CODE   a compile step's error messages: bcerr.bas, bckw.bas

Each also has bcutil.bas (messages, file names, the job file, ChainTo; what
is done once in the library's segment RTSELDOM),
and the first module of each is its main one (tools/bcprogs.py lists
them, for every build tool).  bccom.bas holds the declarations every
module includes, bcgencom.bas those of pass 3 and the listing, bcprocs.bas
the cross-module DECLAREs (generated by tools/mkdecls.py).  lib/*.bas is
the run-time library BASLIB (RTCORE RTFILE RTSTR RTNUM RTARR RTINPUT RTDATA
RTSUBV RTCHAIN; RTCOM their shared header); demos/*.bas the example
programs of the volume's DEMO/.

The job.  BC turns its command line -- or a line typed at its prompt --
with the batch files it names into steps, and writes them to the job file
:BCTEMP.JOB (on the prefix volume): where the programs are ("#u:", the
unit BC's own code file came from: SYSCOM^.SEGTABLE[1].CODEUNIT; the six
must be on one volume, at its top), the options (-Q, -M, and whether BC
asks for the next command), the step being done, and the steps after it:

    C lst NAME       a compile (lst: 1 with a listing)
    L OUT=A,B        a link (a compile without -C is followed by one)
    J LIB=A,B        a join

BC takes the first step off, writes the file and chains to BCLEX (a
compile) or BCLINK.  BCLEX makes the token file and chains to BCGEN; BCGEN
compiles (its tables are arrays made with REDIM) and chains to BCLIST for
a listing; each of them, done or failed, chains to "BC -Z 0" or "-Z 1".  BC
then runs the next step; after a failure it drops the rest (as one failing
command stopped its batch file and its line).  When there are no more,
BC asks for the next command, or -- started with its commands as its
command line -- ends with the last step's status (the shell's exit
status).  A program of the six run by itself finds no job file and says
so.  Nothing else passes between them: the token file, :BCTEMP.DAT (DATA),
the listing's two temporary files and the object file are all files.

## 2. The bootstrap

The compiler exists only as BASIC.  To get the first BC.CODE without a
BASIC compiler, tools/bas2c.py translates each program's modules into one
C file, which gcc compiles with tools/hostrt.h, a C version of the
run-time library, into build/bc, build/bclex, build/bcgen, build/bclist
and build/bclink: BC running on Linux (CHAIN there runs the program of
that name beside the one running: execv).  That build compiles BC's
sources (and the library's) into P-code: build/BC.CODE and
build/BASLIB.OBJ.  On the P-System, BC.CODE compiles the same sources
again and must make the same files.

What makes the two agree:
- One algorithm: the compiler is the same text in both builds.
- The language's semantics in both: 16-bit INTEGERs that wrap, -1/0
  truth, strings of at most 255 characters, CINT rounding a half away
  from 0, LINE INPUT keeping 255 characters (BC's sources keep their
  lines shorter; tools/buildhost.sh checks).
- Left-to-right evaluation.  C leaves the order of a call's arguments and
  of an operator's operands open; bas2c sequences every one that has a
  call in it through temporaries, as BC's own code evaluates it.
- Real constants are made without the host's floating point: VAL (strtod
  on both sides, correctly rounded) gives the double, MKD$ its bytes, and
  integer code turns those into the P-machine's real format.

bas2c handles the part of the language BC is written in (no GOSUB, no
DATA, no SINGLE arithmetic); BC handles the whole language.

## 3. Pass 1: tokens

The lexer reads the source a line at a time (LINE INPUT), cuts off the
comment (' or REM, outside strings), joins " _" continuation lines, and
follows #INCLUDE.  It writes the token file BCTEMP.TOK: a header of 16
words, then a byte stream.  The header is room left at the start, filled
in at the end (SEEK #CHTOK, 1) with what the lexer counted while it read
the source, for BCGEN to size its tables (section 10); THxxx in bccom.bas
are the words' indexes:

    0 TOKMAGIC (16980)
    1 the names at the module's level (DIM SHARED, COMMON, CONST, the
      body's variables, the procedures' names; a label counts twice: pass
      2 and pass 3 each make a symbol of it)
    2 the most names in one procedure (each counted once in it)
    3 the parameters of all SUB, FUNCTION and DECLARE lines;  8 the most of
      one line
    4 the names in CONST lines
    5 the largest procedure's code estimate: 3 bytes a token (not counting
      DECLARE, CONST, COMMON, DEFINT ... lines) and its strings' bytes
    6 the most keywords that make labels and jumps (IF, ELSE, FOR, NEXT,
      DO, LOOP, SELECT, CASE, GOTO, GOSUB, AND, OR ...) in one procedure
    7 the tokens of the longest statement

The byte stream:

    1..99    keywords (KPRINT .. KUSING)
    100..118 operators and punctuation
    128 TIDENT  length, name (upper case, with its suffix)
    129 TINT    a word
    130 TSNG / 131 TDBL  length, the number's text (digits . E exponent)
    132 TSTR    length, characters
    133 TLINE   the line's number (a word), length, its text (for
                messages and the listing)
    134 TLABEL  length, the label (a line number's digits, or a name)
    135 TEOF;   136 TFILE  length, the file the next lines come from

A DATA statement's text is kept as one TSTR.  The keyword table is a few
string constants of 9-character fields searched with INSTR.

## 4. Pass 2: declarations

DeclPass reads the tokens once, following DEFINT and the others in order,
and enters what every procedure may use before its text is compiled:
the SUBs and FUNCTIONs of the module and the DECLAREd ones (name, result
type, parameters with their types and BYREF/array flags, segment,
PRIVATE), DIM SHARED and COMMON SHARED variables, OPTION EXPLICIT, the
DATA statements (into BCTEMP.DAT) and the labels' DATA numbers.

The symbol table: parallel arrays (name, kind, type, storage class,
offset, flags, scope, auxiliary words) and a hash table of chains.  A
procedure's symbols are pushed on top and popped at its end.  Names are
stored with their suffix; a name declared AS a type without one.

## 5. Pass 3: code

The token file is read twice: first the module's body (everything outside
the procedures: one procedure, MODULE'BODY), then each SUB and FUNCTION.
Each procedure is compiled into a byte buffer and written to the object
file when its END is read.

Expressions are parsed into a tree of nodes (one statement's at a time),
typed as they are built: conversions are nodes, integer constants are
folded, a comparison is a "boolean" (1/0 on the stack: FJP tests bit 0)
that becomes -1/0 only when used as a number.  Conditions jump: a = b of
integers is EFJ, a <> b NFJ, ANDALSO/ORELSE are jumps.

Statements are compiled by recursive descent.  A block (the body of IF,
FOR, DO ...) is compiled by GenBlock, which returns the keyword that ends
it.  EXIT and CONTINUE use a stack of the open blocks' labels.

The P-machine as BC uses it:
- Every BASIC procedure is a lex-level-1 procedure.  Calls are CXP
  seg,proc; the linker makes them CGP proc, NOP within a segment.
- Globals (module statics and COMMON variables) are the locals of the
  startup procedure, reached with LDO/SRO/LAO and a 2-byte operand the
  linker fills in.
- A frame: the parameters first (the first pushed first: the last
  parameter is word 1), then the locals.  A FUNCTION's result goes into
  the words of its parameters (the caller pushes room for it when the
  result is bigger) and RNP pushes it.  Locals are set to 0 on entry
  (FILLCHAR), as BASIC wants.
- The entry code (zeroing, saving the string work area's mark) is known
  only at the end: the procedure is made from offset 0 and the entry code
  put in front of it afterwards (an even number of bytes, so LDC and XJP
  words stay aligned); labels, jumps and relocations move with it.
- Jumps are one byte: forward up to 127 bytes, anything else through the
  procedure's jump table (60 targets at most).
- GOSUB pushes the number of its return point on a stack in the library
  (_GSPUSH); RETURN pops it and goes back through a case table (XJP).
- Strings in the code are LSA constants (in the Harvard layout the
  emulator copies them to data space when the segment is loaded).
- SINGLE is the P-machine's real (ADR, SBR ... and its comparisons);
  DOUBLE the emulator's CSP 100..137.

The listing: for each statement the offset its code starts at and its
text go to :BCTEMP.LST, and when a procedure is finished its code (in hex),
its sizes and its relocations (with their names) to :BCTEMP.LCD
(ListSave).  After pass 3 BCGEN chains to BCLIST (ListModule), which reads
both and disassembles the code between the statements: a program of its
own, as the listing's code beside pass 3's was more than the Harvard
layout's 64K code space held (*STK OFLOW*).  While the object, the statements
and the code are written, three new files at once, the object is opened
with [*] (half the largest free area, the operating system's rule) and
the statements' file so too, or the first file would take all the room.

Errors.  BCLEX's and BCGEN's errors are numbers: ErrNo n, or ErrRec n,
a, t, s$ for a message with a number, a token or a string in it (Expect t:
error 1, "{k} expected, not {t}"; LexErr n, s$; FatalRec n, s$ for one
after which the step cannot go on), each with a comment that gives its
text.  BCUTIL's ErrRec keeps the first 30 with where they were (the file,
the line's number and text), in arrays made at the first one; when the
step ends (CompileFailed) they are written to :BCTEMP.ERR, and the
program chains to BCERR.  BCERR has the texts (MsgText$; {s}, {a}, {t},
{k} filled in, KwName$ for a token's name), says each error as the
compiler always did ("FILE line N: text", then the line) and "N error(s):
no NAME.OBJ" (a fatal one: "BC: text", and no more), removes the step's
files and chains to BC with the failure.  So the texts take no memory
while the compiler works: BCGEN's code is 6K smaller.  A new error: a
number after the last, its text in bcerr.bas.  tools/errtest.py compiles
tests/errors/*.bas (full of mistakes) on the host and on the P-System and
compares what is said with tests/errors/*.expect.

## 6. Strings

A string is a pointer to a Pascal string (a length byte, the characters),
0 for "".  A variable owns a heap block.  The strings an expression makes
are temporaries in a 1.5K work area: a procedure keeps the work area's top
(_TTOP) on entry and puts it back after every statement that made
temporaries, and on both ways out of a condition.  A callee therefore
never overwrites its caller's temporaries.  A string's owner is told by
its address: a block between the heap's start and its top is a
variable's; a temporary or a constant is not (assigning one to a
variable copies it).  A BYVAL string argument is passed as a temporary
copy; a FUNCTION's string result is copied to the caller's work area
(_SRET) and the callee's variable given back.

## 7. The object file

    "BCOB"  'M' module name
    'P' flags, name, segment, parameter bytes, result words, length,
        jtab, the procedure's bytes, then its relocations (position,
        kind, name): 1 a call (CXP), 3 a module static's operand, 4 a
        COMMON variable's operand
    'D' 0, name, words      a COMMON variable
    'G' words               the module's statics
    'E'

A library is modules one after another (-J).  flags: 1 the module's body,
2 a PRIVATE procedure (its name is MODULE'NAME).  Names of the run-time
library start with an underscore and have no type suffix.

## 8. The linker

It reads the object files and the library from the start, never seeking:
pass 1 enters every module, procedure and COMMON variable and the names
each procedure uses; the linked procedures are the main program's body,
the library's start and end (_RTINIT, _HALT), whatever a linked
procedure calls, and the body of each module one of whose procedures is
linked (a procedure no one calls is left out: PI's code file has 7K of
the library's 13K); a segment longer than 32000 bytes is an error; the
layout puts each linked module's statics and the COMMON variables after
word 3 of the startup procedure's frame, numbers the segments (the main
one 1, the others 7, 8, ...) and the procedures; then, for each segment,
the files are read again and its procedures written, their calls and
operands filled in.  Block 0 (the segment dictionary) is known before the
first segment is written.

The startup procedure (segment 1 procedure 1, lex level 0) clears the
globals, calls _RTINIT, the bodies of the modules (the main program's
last) and _HALT(0).

## 9. The run-time library

BASLIB is BASIC compiled by BC.  It works on addresses with PEEK, POKE,
CSP (MOVELEFT, FILLCHAR, UNITREAD/UNITWRITE, NEW, RELEASE, MEMAVAIL ...)
and OSCALL (FINIT, FOPEN, FCLOSE, FBLOCKIO).

- The heap: blocks up to 32 words in lists by size (multiples of 4
  words); bigger ones in one list by address, joined with free
  neighbours, cut when much bigger than asked, and given back to the
  P-machine (RELEASE) when they are the heap's last.  _NEWBLK keeps 500
  words for the stack and records the least free memory (FRE(-1)).
- Arrays: a block with the number of dimensions, the element size (and a
  string flag), each dimension's count, the elements; _AX1, _AX2, _AXN
  check the indexes and give an element's address.
- Files: 15 channels; the text file format (header, pages, DLE) and the
  buffering are the library's, ported from Tiny-C's stdio.  Every block
  goes through _BLOCKIO: FBLOCKIO for a file the operating system opened,
  RTSUBV's _SVIO for one in a sub-volume.
- The segment RTSELDOM holds what a program does seldom, so that it is in
  memory only then: OPEN and the file names it takes (RTFILE), the
  sub-volumes (RTSUBV), CHAIN (RTCHAIN), the command line at the start
  (_ARGS); BC's seldom parts too (bcutil.bas, the end of a procedure in
  bcemit.bas).  _ERRTEXT stays in the main one: an error for want of
  memory still has its message.
- Sub-volumes (RTSUBV): a path VOL:/A/B/NAME is
  followed as Tiny-C's library does it, but the first step is the OS's:
  FOPEN of VOL:A gives its unit (FIB word 7) and first block (FHEADER's
  DFIRSTBLK, word 16), so #5:, * and the prefix work as for any file; the
  file is closed at once.  Then each directory (blocks 2..5 of the
  sub-volume, 2 KB read for the open and given back) leads to the next,
  and the file is read and written with UNITREAD / UNITWRITE at its own
  blocks: the channel entry keeps the unit, the sub-volume's and the
  file's first blocks, the blocks it may use and the blocks it has.  A new
  file takes the largest free area; when another file being written is
  in it, the new one takes the second half of what that one has left
  (and that one's limit becomes the first half), so two files can be
  written into one sub-volume at once (BC: an object and its listing).
  CLOSE writes the directory entry (an old one of the name goes; the date
  is the boot disk's), and only when a file is new or longer; a new file
  that could not be written whole is not entered.  KILL removes an entry.
- Numbers: text with DTOA (CSP 133) and BASIC's style; VAL with ATODM
  (CSP 135).
- The console: a line buffer written with UNITWRITE, whose control word
  has CRLFBIT (8): the console adds no LF after a CR, so CHR$(13) goes
  back to the line's start, and _PNL ends a line with CR and LF (on the
  console, or a file opened as CONSOLE:).  Input is read a key at a time
  with UNITREAD and echoed (the echo of RETURN with its LF).
- CHAIN (RTCHAIN): Tiny-C's
  pexec without the way back.  _CHAIN finds the code file as pexec does
  (a path or the shell's path: RTSUBV's _SVPATH; else FOPEN of NAME.CODE:
  the FIB's unit and first block), checks that it is a linked code file
  (block 0's SEGKIND), puts the line into PL (with the shell's path after
  a byte 30) with PX_ARGS and its checksum, the code file into
  EXPANSION[1..2], sets EXPANSION[0] = PX_RUN and ends the program
  (_HALT).  GETCMD then runs the other one; when that ends GETCMD starts
  the code file of EXPANSION[3..4]: unchanged when this program is a
  child of the shell's (PX_CHILD), so the shell comes back; else unit 0,
  no code file, so the Command: prompt.  bas2c translates CHAIN for the
  host build: the host program of that name beside the running one.
- COMMAND$ follows Tiny-C's pexec protocol (SYSCOM^.EXPANSION, the OS's
  prompt line PL); the exit status goes to EXPANSION[5].  _RTINIT takes
  the line once, at the start (_ARGS): the arguments for COMMAND$, and
  the shell's path (CD) after them (a byte 30 before it).  _OPEN and
  _KILL put that path before a name without a volume (_FNAME, as Tiny-C's
  library does), so a program run after CD BASIC:/DEMO finds PI.BAS there.
  _FNAME also takes a size off the end of a name, [n] or [*], which only
  the operating system's FOPEN is given (a file in a sub-volume has none).
- Text files: a name ending in .TEXT or .BAS.  A new one is entered with
  the kind text whatever the operating system makes of its name: before
  FCLOSE the library sets the FIB's FHEADER.DFKIND to 3 (FCLOSE copies
  FHEADER into the directory); in a sub-volume the entry is the library's
  own.  An old file is read as text by its name, whatever its kind (a
  NAME.BAS the Editor wrote under an older system is a data file).

The library's procedures pass strings as INTEGER pointers, so the
compiler cannot know when one makes a temporary it does not hand back
(_PINT printing a number's text): such a procedure gives the work area
back itself (t = _TTOP ... _TTOP = t), or a loop of PRINT #n, i would
fill it.

## 10. Memory

BC is written for the Harvard layout (code in its own 64K instruction
space), where each of its programs has about 30000 words of data space;
compiling itself, the least any has left is about 9500 words.  It runs in
the other layouts too, where its code takes data space: the Z80 mode (the
least memory) and P-Code mode without the Harvard layout (3900 words
more), for programs the size of the demos -- tools/smalltest.py compiles,
links and runs PI in both.  What makes that fit:

- The linker links procedures, not modules (section 8): the library's
  13K of code was in every program; now only what it calls is (BC's own
  programs are 5 to 6K smaller, PI 7K).
- The segment RTSELDOM (section 9): the library's and BC's seldom parts.
- BCGEN's pass 3 is six segments, a call chain holding three of them at
  most: STMT (the statement loop: GenBlock, GenStmt, IF, FOR, DO, WHILE,
  SELECT); one of STMTA (assignments, calls, GOTO, GOSUB, ON, EXIT),
  STMTD (DIM, CONST, SHARED, STATIC) and STMTIO (PRINT, INPUT, the files,
  READ); and EXPR (an expression parsed into a tree) or EXPRGEN (its
  code): an expression is parsed, then made into code, so those two are
  never in memory together.  What all of them use (the emitter, the
  nodes, the symbol lookups, GenPass and GenProc) is in the main segment.
  The error messages' texts and the keywords' names are BCERR's (section
  5): BCGEN holds none (BCLEX's KwCode keeps a copy of the keyword table);
  ProcHeader and CountDims, which only pass 2 uses, are in DECL.
- BCGEN's tables are as large as the token file's header (section 3)
  says the source needs, their MAX constants at most: the symbols (the
  module's names, the most of one procedure, and 48 for the run-time
  library's procedures a procedure calls, which pass 3 enters as symbols),
  the parameters (all of them, and one line's again: pass 3 reads each
  procedure's parameters after them), the string and real constants --
  these are never too few -- and a procedure's code (its estimate and 104
  bytes), its jumps (2 a keyword of word 6, and 8), labels (3 a keyword,
  and 8), calls (one for every 8 bytes of the code's estimate, and 24) and
  an expression's nodes (half the longest statement's tokens, and 16),
  which are estimates.  -M shows the sizes ([tables: ...]) and the most of
  each that was used ([high: ...]).  When one is full, REDIM PRESERVE makes
  it 100 entries larger (Grown): of BC's sources, the library, the demos
  and the tests only the test DATA's calls need that, once.  BCLINK's
  tables (names, procedures, modules, references, COMMON variables; its
  buffer is the largest procedure's size) start small and double when
  full (LinkGrown) -- they grow far, the references to thousands, and each
  step leaves the old table's memory behind as a hole too small for the
  next one.

Compiling PI, BCGEN has at least 2180 words left in Z80 mode and BCLINK
3530 (6100 and 7440 in P-Code mode without the Harvard layout).  BC's own
modules need more than either has, in the symbol table (up to 640
symbols, 8 words each) and in their deeper statements: compiling itself
needs the Harvard layout.  BC does not check the layout; out of memory, it
says Run-time error 7, or the emulator *STK OFLOW*.  (bas2c takes the CSP
statement as nothing and CSP%() as 0.)

## 11. Testing

- tools/importtest.py: a Windows PI.BAS imported with the emulator's
  Import File (run_verify's VERIFY_IMPORT; emulator 2.10 makes it a text
  file), compiled, linked and run with BC, exported back the same.
- Errors: _RTERR closes every file; an error while it does (a CLOSE that
  cannot write) ends the program at once, and _CLOSE1 marks a file closed
  before it reports, so the two do not call each other until the stack
  overflows.
- tools/runtests.py: tests/NAME.bas compiled by the host build, run on
  the emulator, compared with NAME.expect (NAME.keys: what is typed;
  NAME.dirs: sub-volumes made on the work disk first and listed by the
  host afterwards: tests/subvol).
- tools/selfcompile.py: BC and BASLIB rebuilt on the P-System, compared
  with the host's.
- tests/chain (NAME.progs: the programs it chains to) and tools/chaintest.py
  (CHAIN from programs the shell started: the shell back with the last
  one's exit status; the shell's path along the chain; --pascal).
- tools/mkvolume.py makes build/BASIC.BLK (the sub-volumes SRC, LIB, DEMO,
  TEST with TEST/EXPECT, each made on the host as a volume written into
  the volume as a data file, with room for twice what its batch file
  writes, measured with the host build, and 40 blocks); tools/voltest.py
  runs @BASIC:ALL and -S BASIC:/DEMO/PI on it (BC2.CODE, LIB/BASLIB2.OBJ and
  the listing must be the host's,
  every demo and test gets its code file, the directories must hold
  together) and runs a demo and a test from their sub-volumes; then, in the
  shell, @BASIC:INSTALL (BIGGY 1.32's batch files) puts BC2.CODE ... in the
  places of BC.CODE ..., and that compiler makes DEMO/HELLO, which runs;
  --pascal boots BIGGY's SYSTEM.PASCAL instead of SYSTEM.C.
- tools/brun.py runs a code file; tools/objdump.py shows an object file;
  tools/pdis.py disassembles a code file.
